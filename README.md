# SpecGuard AI

ИИ-агент, который проверяет документ с требованиями **до начала разработки**. Он находит двусмысленные, непроверяемые, противоречивые и неполные формулировки и пишет отчёт на русском языке. Каждое замечание подкреплено точной цитатой из документа: программа сама находит эту цитату в тексте, поэтому модель не может её выдумать.

Критерии проверки: ISO/IEC/IEEE 29148:2018 (п. 5.2.5, 5.2.6) и IEEE Std 830-1998 (п. 4.3).

## Как запустить прогон

Нужен Python 3.12 или новее.

**1. Получите бесплатный ключ** на <https://openrouter.ai/settings/keys> (вход через Google или GitHub). Вместо него или вместе с ним подойдёт ключ Gemini из Google AI Studio: <https://aistudio.google.com/apikey>.

**2. Установите агента и вставьте ключ:**

```bash
python -m venv .venv
. .venv/bin/activate            # Windows: .venv\Scripts\activate
pip install -e .
cp .env.example .env            # откройте .env и впишите ключ в OPENROUTER_API_KEY= (или GEMINI_API_KEY=)
```

**3. Запустите проверку одной командой:**

```bash
python -m app.cli --input docs/requirements.md --output output/report.md
```

`--input` — путь к документу (`.md` или `.pdf` с текстовым слоем), `--output` — путь к отчёту. Выданный организаторами документ в репозиторий не входит: положите его в `docs/requirements.md` или укажите свой путь.

**4. Откройте отчёт.** Он запишется в `output/report.md`, рядом появятся `report.html` (удобно читать в браузере) и `report.json`.

В терминале виден ход проверки. На бесплатных моделях прогон занимает от нескольких минут до 20–25 минут, это зависит от загрузки моделей.

## Что в отчёте

| Раздел | Содержание |
| --- | --- |
| 1. Паспорт прогона | документ, дата, модели каждого этапа, версия агента (git-коммит), статус |
| Вопросы аналитику | решения, без которых разработку начинать нельзя |
| 2. Как агент нарезал требования | таблица «ID в отчёте — ID в документе — краткая формулировка» |
| 3. Проверка каждого требования | 9 критериев качества для каждого требования |
| 4. Проверка всего набора | полнота, согласованность, реализуемость, понятность, возможность валидации |
| 5. Замечания | цитата, объяснение, последствия, вариант исправления |
| 6. Сводка | число требований и нарушений, список критичных дефектов |
| 7. Итог | можно ли начинать разработку и тестирование и что исправить в первую очередь |

## Какая модель используется

Основной провайдер — [OpenRouter](https://openrouter.ai), запасной — Google Gemini API. По умолчанию используются только **бесплатные** модели, платный ключ не нужен.

| Задача | Модель по умолчанию |
| --- | --- |
| Проверка требований и набора | `nvidia/nemotron-3-ultra-550b-a55b:free` |
| Выделение требований, исправления, независимая перепроверка | `nvidia/nemotron-3.5-super-vl:free` |
| Запасные, если основная недоступна | `inclusionai/ling-3.2-flash:free`, `particle-ai/particle-1:free`, `google/gemma-4-31b-it:free` |

**Gemini на всякий случай.** Если задан `GEMINI_API_KEY`, агент работает и через Google Gemini API:

| Какие ключи заданы в `.env` | Что происходит |
| --- | --- |
| только `OPENROUTER_API_KEY` | работают модели OpenRouter из таблицы выше |
| только `GEMINI_API_KEY` | работают `gemini-2.5-flash`, запасная `gemini-2.5-flash-lite` |
| оба | сначала OpenRouter, Gemini подхватывает запросы, если модели OpenRouter недоступны или кончился лимит |

С `LLM_PROVIDER=gemini` первым идёт Gemini. Квоты бесплатного тарифа Gemini меняются, актуальные значения смотрите в AI Studio.

Модели можно сменить в `.env`. В паспорте отчёта указано, какая модель реально выполнила каждый этап.

На бесплатном тарифе OpenRouter даёт 50 запросов в сутки. Один прогон тратит примерно 10–14 запросов, так что в день помещается 3–4 прогона. Перед стартом агент проверяет ключ и остаток лимита.

## Как агент проверяет

1. **Нарезка.** Программа делит документ на фрагменты и запоминает их координаты. Модель только группирует готовые фрагменты в требования, переписать текст она не может.
2. **Программные правила.** 11 проверок без модели находят явные дефекты, например GET для сохранения данных, незаполненные шаблоны, «TBD».
3. **Проверка модели.** Сначала каждое требование по отдельности, потом набор целиком (противоречия, пропуски), потом финтех-сценарии: возвраты, повторные события, границы месяца.
4. **Проверка доказательств.** Программа ищет каждую цитату в документе. Если цитаты нет, замечание отбрасывается. Затем отдельная модель пытается опровергнуть каждое замечание.
5. **Отчёт.** Его формирует программа. Оценка готовности считается детерминированно.

Если какой-то этап не выполнился, отчёт получает статус «частичный» и не выдаётся за полный.

Подробнее: [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

## Ограничения

- Текст документа уходит в OpenRouter и поставщику модели. Не загружайте конфиденциальные документы.
- Ответы модели могут немного отличаться от прогона к прогону. Правила, поиск цитат и оценка детерминированы.
- PDF-сканы без текстового слоя и DOCX не поддерживаются.
- Это локальный прототип, авторизации нет. Проверки из веб-интерфейса хранятся в `.data/analyses` без шифрования и удаляются кнопкой в списке.

## Дополнительно

**Веб-интерфейс** (нужен Node.js 20+): загрузка документа, ход проверки, интерактивный отчёт.

```bash
cd frontend && npm ci && npm run build && cd ..
python -m app.main               # откройте http://127.0.0.1:8000
```

**Полезные флаги CLI:**
- `--rules-only` — только программные правила, без модели и ключа. Отчёт помечается частичным.
- `--cache` — для отладки, повторно использует сохранённые ответы модели. Такой отчёт помечается отладочным.

Коды выхода: `0` — полный отчёт, `2` — частичный, `1` — ошибка.

**Тесты и оценка качества:**

```bash
pip install -e '.[dev]' && pytest
(cd frontend && npm test)
python -m app.evaluate --report output/report.json   # сверка отчёта с 18 размеченными дефектами учебного документа
python -m app.evaluate --dataset                     # 40 дефектов и 8 корректных кейсов (около 32 запросов к модели)
```

Размеченный набор небольшой, поэтому метрики показывают порядок величины, а не статистически значимую точность.
